## Vim との格闘

https://github.com/Quramy/zakki/blob/main/docs/memo/202512.md#1227 にて、 Vim の +python3 ビルドが通らない件について書いたが、結局のところ、mac のデフォルトの python3 が利用されていたことが原因だった模様。

> ```sh
> ./configure \
> --prefix=/Users/quramy/opt/local \
> --with-features=huge \
> --enable-python3interp \
> --enable-fail-if-missing
> ```
>
> 上記を実行すると、以下のような Python の config dir がない、と言われる
>
> checking Python's install prefix... (cached) /Library/Developer/CommandLineTools/Library/Frameworks/Python3.framework/Versions/3.9
> checking Python's execution prefix... (cached) /Library/Developer/CommandLineTools/Library/Frameworks/Python3.framework/Versions/3.9
> checking Python's include path... (cached) /Library/Python/3.9/include
> checking Python's include path... (cached) /Library/Python/3.9/include
> (cached) checking Python's configuration directory... (cached)
> can't find it!

デフォルトの python3 で以下を実行して Config dir を確認してみると、

```python
import sysconfig;
print(sysconfig.get_config_var('LIBPL'))
```

以下のような値が返ってくるのだが、そもそも Xcode をインストールしていない状況であるため、それが存在しないと configure から言われるのは当然であった。

```
/Applications/Xcode.app/Contents/Developer/Library/Frameworks/Python3.framework/Versions/3.9/lib/python3.9/config-3.9-darwin
```

そもそも python3 は Homebrew でインストールしていたものを使うつもりで brew もインストールしていたが、シェルの環境変数に brew のパスが優先されていなかったので、デフォルトの python3 が利用されいた。brew の python3 を利用するようにするために、以下のコマンドを実行して環境変数を設定する必要があった。

```sh
eval "$(/opt/homebrew/bin/brew shellenv)"
```

また、configure を叩き直す前に `make distclean` を実行して、configure のキャッシュをクリアしておかないと古い値が使われてしまうため、これも忘れずに実行する必要があった。

# 8/14

## Terraform の環境構築

初めてローカルで Terraform を使う状況になった。

教科書的には以下で済むのだけど。。。

```sh
terraform init
terraform plan
```

実際に init してみたら GCP 周りで色々言われる羽目になる。

init / plan 両方とも tfstate が格納されている GCS バケットにアクセスする必要があるが、まずこの権限確認を gcloud 経由で行った(正確には claude code にやってもらった).
対象プロジェクトの tfstate が格納されているバケットで ls などができることを確認した後に `terraform init` を実行したのに、403 が出てしまう。

結局それも claude に解決してもらったわけだが、terraform は ADC で設定された資格情報を使って GCP の操作を行うが、ここで必要なのは `gcloud auth application-default login` で設定される ADC であり、 `gcloud auth login` で設定されるユーザー認証情報ではない、とは別ものであり、且つ自分の ADC は(同じ Google アカウントに紐づいた) 別の GCP プロジェクトのママであったため、ADC の quota-project ID が terraform の対象プロジェクトと異なるために GCP に弾かれた、という経緯。

ADC (Application Default Credentials) は耳にしたことはあったものの、何かの認証情報っしょ程度の浅い理解だったが、今回の件で調べて少し理解が深まった。
多分昔でいう Service Account JSON の代替で、GCP の SDK を利用するアプリケーション(今回のケースだと terraform) が GCP アクセス時に利用する認証情報も ADC によって提供されている。
gcloud cli 自体は ADC と関係なく `gcloud auth login` と project id 指定すれば動いてしまうために、gcloud cli を使った権限確認だけでは気づけなかったという顛末。

インフラ慣れている人からしたら当たり前すぎる話なのかもしれないが、自分には学びのある詰まりだった。
あと、AI 無かったら挫折していたこと間違いなしで、今回はインフラ系の作業且つ自分にとって実績も自信もない範囲の話だったので、セッション中で実行するコマンドは逐一 claude 側から許可取らせるようにしてやっていたこともあり、時間はかかったものの、結果的にはよかったと思う。もし、auto mode でやっていたら気づいたら終わってた、となってたかもしれない(まぁ `gcloud auth application-default login` が claude だけだと完結しないからそこで中断された可能性高いけど)。
