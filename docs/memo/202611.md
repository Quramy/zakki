## Interop 2027 の候補とランキング

https://interop-rank.fxdx.dev/ で Interop 2027 で取り上げて欲しい機能に投票が行える。

https://github.com/web-platform-tests/interop/blob/main/2027/selection-process.md によると、以下のタイムラインで進むとのことなので、ちょうど現在も投票期間の模様。

> - Proposal submission window (~3 weeks): September 3rd, 2026 to September 23rd, 2026
> - Proposal selection: Before December 10th 2026
> - Scope of the Interop 2027 project published: February 4th, 2027.

かるくみて興味あるものをピックアップしてみた。気づいたら全部 CSS やんけ

1. [CSS `var()` in size container queries](https://github.com/web-platform-tests/interop/issues/1344). Such as `@container (width >= var(--min-width))`.
2. [Responsive iframes](https://github.com/web-platform-tests/interop/issues/1443). The `frame-sizing` CSS property sizes an `<iframe>` to its content, avoiding scrolling within the iframe.
3. [CSS `line-clamp` property](https://github.com/web-platform-tests/interop/issues/1379). Limits the text in a block container to a certain number of lines. Also allows custom end text if content overflow occurs.
4. [CSS container scroll-state queries](https://github.com/web-platform-tests/interop/issues/1364). The `@container scroll-state(...)` at-rule applies styles based on the sticky positioning, snapped, and scrollable state of the container.
5. [CSS grid lanes (masonry)](https://github.com/web-platform-tests/interop/issues/1445). `display: grid-lanes` creates a layout where items are tightly packed into parallel lanes.

## Kitesurf by Cloudflare

https://kitesurf.dev/

エージェントからの実行を想定した Web ブラウザ。タブとかテーマのような機能は削減されている。
Cloudflare が実装している。Chromium や WebKit などの既存エンジンは使わずに Rust でフルスクラッチに実装しているらしい。

Chromium と比べて CPU/メモリ効率がよいため、エージェントのワークロードでブラウザアクセスが必要なケースで有効、ということの模様。
当然 Cloudflare worker でも動かすことができる。

## Devin の blueprint について

https://docs.devin.ai/ja/onboard-devin/environment/blueprints

Devin のセッションはスナップショットイメージから起動される。

Docker に例えると、以下のような対応関係。

- スナップショット: Docker Image
- セッションが動作する環境: Docker Container

スナップショットを構成するのに利用する設計書が blueprint である。より正確には blueprint はスナップショットのビルド時以外にも効く箇所はある (e.g. ナレッジの宣言などはセッション開始時にしか意味を持たない)。

たとえば SPA の開発レポジトリであれば、以下のように記載しておくことで、スナップショットがビルドの時点で依存パッケージがダウンロードされた状態になっているため、各 Devin のセッションで都度ダウンロードする必要がない。

```yaml
maintenance: |
  pnpm i
```

スナップショットのビルド時点からロックファイルが変更されていたとしても、 `maintenance` に記載された情報はセッションのコンテキストに共有されるため、エージェントが判断して再度実行することもできる。

blueprint は基本的にレポジトリの単位で設定を行うものだが、スナップショットはあくまで組織に対して１つビルドされるものである（もしかしたら契約プランによって異なるかもしれない）。

なので、ここは Docker のベースイメージのようなマインドモデルとは明確に異なる。

どちからというと、複数の blueprint から `COPY` や `RUN` をかき集めて Dockerfile を一個用意し、Docker Image をビルドしているようなイメージに近い。
