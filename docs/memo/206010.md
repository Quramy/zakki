## AI-DLC について

AI-DLC とは、 開発プロセス(要件定義 ~ 開発 ~ 運用) 全体で AI を介在させる、というソフトウェア開発論。
初出は AWS DevSphere 2025

https://aws.amazon.com/jp/blogs/devops/ai-driven-development-life-cycle/

- https://speakerdeck.com/hiroramos4/aidlc-casestudy
- https://www.beex-inc.com/column/realities-of-ai-driven-development

AI-DLC はツールを規定するわけではないが、以下の 3 つのフェーズ全てに AI を利用することを前提とする。

- Inception: 要求を AI が独立実装可能な単位(= Unit と呼ぶ) に分割する
- Construction: Unit 毎に AI が設計/実装/テストを行う
- Operation: 運用や障害対応

Inception -> Construction で正しくコンテキストを伝えていくため、Kiro や GitHub Spec Kit のような仕様文書を管理するフレームワークの利用が前提となる。
Jira や Confluence, Google Drive 管理でも不可能ではないだろうが、Context を適切に伝播させることを考えると、何かしらのフレームワークで文書管理されているのが望ましいらしい。

AI-DLC の本質は「AI の開発スピードに合わせた人間側のプロセスの最適化」であると思った。
AI-DLC では "Mob Elaboration" や "Mob Construction" という儀式を重視している。これは、関係者を一同に集めて AI の問答に答えて、成果物の承認を行うというもの。
PR レビューもそうであるが、今やソフトウェア開発のボトルネックは PR の作成ではなく、そのレビュー側となっているのは火を見るよりも明らか。

これを愚直に解釈すると、Inception でも mob, 分割された Unit の Construction でも mob、のような「何でもかんでも mob」というプロセスになりかねない。
また、「関係者一同を集めて mob ができるのは N 日後」のようなことになったら結局のところろ AI-DLC の提唱するボトルネックの解消には繋がらない(下手をすると悪化しかねない)。

このような mob の基準については各所でも指摘されているようで、例えば以下の資料にも「不確実なものはモブ、再現可能なもの・ゴールが明確なものは個人+AI」とある。

https://speakerdeck.com/hiroramos4/aidlc-casestudy?slide=12

## NPM Trusted Publishing の穴について

https://thehackernews.com/2026/10/github-tightens-npm-publishing-after.html のニュースにて、以下の変更が報告されている。

> GitHub has taken the step of expiring unvalidated npm trusted publishing configurations 48 hours after creation

NPM Trusted Publishing について、設定後 48 時間以内に設定の妥当性の検証が行われない場合、設定が無効化される、ということと思われる。

GitHub 側の[公式リリース](https://github.blog/changelog/2026-10-02-unvalidated-npm-trusted-publishing-configurations-now-expire/) によると、検証とは `npm publish` そのものを指す。

この変更がどのような攻撃への防御を意図しているのか、よくわからなかっのだが、この問題を GitHub 側に報告した Bloom Security が書いた記事が以下。

https://bloom.security/blog/slugfest-millions-of-ai-agents-download-exposed-npm-packages

NPM 側で設定したのみの Trusted Publishing は、GitHub の `<owner>/<repo>` (と publish に利用される workflow ファイル名)の文字列情報しか持っていない。
一度でも OIDC Token を使って CI から `npm publish` を行えば、Repository ID (これは不変な ID) が NPM Registry に送信されて記憶される。

- 正規メンテナ: あるレポ `fuga-org/hoge` にて NPM Trusted Publishing の設定を行う
- 正規メンテナ: Trusted Publish を行う前に、`piyo-org/hoge` にレポジトリを移管する
- 攻撃者: 移管元である `fuga-org/hoge` の GitHub の管理権限を取得する

上記の条件が成立すると、攻撃者は `fuga-org/hoge` のレポジトリから該当パッケージへ Trusted Publishing が可能であり、NPM のトークン無しでサプライチェーンアタックを成立させたことになる。

正直、上記の前提を満たすのがそんなに簡単ではないと思うのだが、Bloom の blog によると 1,500 超のレポジトリがこの攻撃を受ける危険性があるらしい。

> To understand the in-the-wild exposure, we built a scanner that tests the ability to perform the attack end-to-end - we started by checking which packages have trusted publishing configured. We then checked the repositories and their owners to validate which are claimable.
>
> We found over 1500 packages vulnerable,

Trusted Publish の設定 (特に owner 名) に typo がある、とかそういうケースだろうか？

## `govulncheck` の概要

NPM における `npm audit` のような位置付け。
Go 言語における標準的なパッケージの脆弱性チェックツール。以下で実行可能。

```sh
govulncheck ./...
```

NPM と違い、 govulncheck そのものは Critical / High のような脆弱性の深刻度を判定する機能は持たない。
脆弱性の深刻度は、Go 言語の脆弱性データベースに登録されている情報を参照する。
