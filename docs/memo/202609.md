## エージェントに丸投げしすぎて自分の知識が身につかない件

新しい職場で Go 言語による機能実装を行ってみたが、Claude に丸投げしただけなため、全然自分の身に着いてない。
これで仕事が成り立ってしまうのであれば、言語の知識など身につける必要がないということの証左になってしまいそうで嫌だ。

API 実装自体が久々だったが、そういえば 4, 5 年ほど前にやっぱりたまたまバックエンド側をやっていたときのことを思い出す。
当時は Rails + graphql-ruby なスタックでの仕事だったが、Active Record の使い方や RSpec の書き方を一つ一つ学んでいって、実地で身につける感覚があった。
今回もプロトコルは GraphQL だったので、そういう意味では似ているところがあり、比較できてしまう分、物悲しさが目立つ。
Schema 設計ってこういう感じだった、N+1 発生するときは Data Loader Pattern、とかそういう知識は役に立っているが、実装の詳細知識はもはや不要になってしまうんだろうか。

ここ 1,2 年で散々擦られ切った話題ではありそうだが、実体験として「これはもうプログラマは不要かもしれない」という気持ちになってきてしまう。

## Dependabot Secret と GHA の `pull_request_target`

仕事にて `on: pull_request_target` な workflow があり、CI が意図通りに動作しない、という状況に直面した。
ちゃんと確定していないが、 `pull_request_target` は base repository のコンテキストで動くことに由来して、target branch の情報が参照されずに CI として偽陰性の方向に動いていた。
他の 3rd party action に依存する箇所のため、裏どりが必要そう。

で、問題はなぜ当該 workflow が `on: pull_request_target` で書かれていたのか、これを `on: pull_request` にできないか？という点になるわけだが、当時の PR を参照してみると、 「Private Repo で dependabot が Open する PR に当該 3rd party action への Secret を渡すため」という趣旨のコメントが残っていた。
確かに、「dependabot private repo secret」などでググると、`on: pull_request_target` を使おう、という記事が幾つか hit した。

ところで、「Dependabot に渡す Secret 」は通常の Repository Secret とは別にきちんと定義されいて、こちらを使えば問題なさそうである(Opus 調べ。自信では未検証)

https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/manage-your-dependency-security/configure-access-to-private-registries#adding-a-repository-secret-for-dependabot

2026 年前半、Trivy や TanStack への攻撃が話題に上がったが、どちらも `on: pull_request_target` な workflow が標的であった。
あれらの事件をきっかけに、 「`pull_request_target` は危険」という意識は醸成されてきているとは思う。

今回は Private Repo で forked な PR が来ることはそもそもない、という考えは成り立たず、攻撃が成立するパターンが考えつく。

事前に NPM や PyPI で自分等が利用しているパッケージの Publish Token が盗まれている、という状態について、攻撃者がパッチリリースを作りこれが Minimum Release Age などをすり抜けて Dependabot に回収されて PR 作成されてしまうと、Secret 参照できる状態で汚染された post install hook が実行され、Repo Secret が盗まれる。
実際、TanStack がやられた Mini Shai-Hulud キャンペーンのワームは CI, Server, Local からトークンを引っこ抜くようなワームであったような記憶。
